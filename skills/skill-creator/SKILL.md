# Skill Creator

指导你创建、修改和优化 Agent 技能（skills）。核心方法论对所有 Agent 通用。

核心循环：**捕捉意图 → 起草 → 测试 → 用户评估 → 改进 → 重复**。顺序可以灵活，但不要跳过“把结果交给用户看”这一步。

---

## 技能结构

一个技能通常是一个目录：

```
my-skill/
├── SKILL.md      # 必需：技能的指令本体
├── references/   # 可选：长文档/多领域细节，按需读取
├── scripts/      # 可选：可复用脚本/工具
└── assets/       # 可选：模板、图标、样式等
```

也可以只有一个 `SKILL.md` 文件。技能名用 `name` 字段标识，建议使用小写字母、数字、连字符（如 `skill-creator`）。

`SKILL.md` 以 frontmatter 开头：

```yaml
---
name: my-skill
description: 这个技能做什么 + 什么时候用
---
```

- `name`：技能标识。
- `description`：触发依据。要写清“做什么”和“什么时候用”，可以写得稍微“pushy”，把同义表达、隐式场景都列进去。例如：“用户提到仪表盘、数据可视化、内部指标，或想展示任何公司数据时都要用，即使没明说‘dashboard’”。

### 资源文件怎么用

- **references/**：正文较长（约 500 行以上）或涉及多领域/多框架时，把细节拆到这里，正文只写“什么情况读哪个文件”。大文件建议带目录。
- **scripts/**：放确定性、可复用的脚本，让 skill 直接调用，避免每次重复实现。
- **assets/**：放输出时要用的模板、图标、样式等。

## 创建流程

### 1. 捕捉意图

先弄清用户要什么，不要急着写文件。可以从对话历史提取已有工作流（工具、步骤、纠错、输入输出），也可以直接问：

1. 这个 skill 应该让 agent 能做什么？
2. 什么时候应该触发？用户会说什么话/出现什么上下文？
3. 期望的输出格式是什么？
4. 要不要设测试用例？（可客观验证输出的技能值得做测试；偏主观风格类的可跳过定量测试，但至少要人工看效果）

### 2. 调研

- 先看当前环境已有的技能，避免重复造轮子。
- 如果目标平台/API 有官方文档，先查证再写进 skill。
- 需要时用 subagent 并行调研，减少用户等待。

### 3. 起草 SKILL.md

按上面的结构写。正文注意：

- **渐进披露**：正文保持精简，长文档放 `references/`。
- **多领域组织**：一个 skill 支持多个领域/框架时，用 `references/` 按变体拆分，正文只做选择路由。
- **用祈使句**，多解释“为什么”，少用空泛的 “ALWAYS/NEVER” 大写恐吓。
- **给出具体输出模板和示例**，让 agent 有可模仿的形。

推荐结构：

```
my-skill/
├── SKILL.md
└── references/ (可选)
```

### 4. 测试与迭代

1. 起草后先出 2–3 个真实感测试 prompt，给用户确认：“这些测试用例看起来对吗？”
2. 记录每个测试的 prompt 和期望结果，作为后续对比基准。
3. 有 subagent 时，用 **with-skill vs without-skill** 对比：
   - with-skill：让 subagent 按技能完成测试 prompt。
   - without-skill：同样 prompt 但不给技能，作为 baseline。
   - 改进已有技能时，baseline 用旧版本。
4. 跑完后把两类结果都展示给用户看，收集反馈；不要只自己判断。
5. 根据反馈改进，重跑下一轮。循环到用户满意、反馈全空、或没有实质进展为止。
6. 如果多个测试用例都写了同样的辅助脚本，就把这段逻辑固化进 `scripts/`，让 skill 直接复用。

没有 subagent 时（或用户只想快速“vibe”）：直接按 skill 逐条执行测试 prompt，把输出给用户看，人工反馈迭代。

### 5. 描述优化

description 决定触发准确率。创建/改进完后可以这样做：

1. 生成一组触发评估 query：一部分应该触发（should-trigger），一部分不应该触发（should-not-trigger）。
   - should-trigger 要覆盖不同说法（正式/口语、同义表达、不点名技能但明显需要的场景、边缘用法）。
   - should-not-trigger 要选“近误”——关键词像但实际不需要该技能的场景，不要选明显无关的。
   - 每条都要具体真实，带点上下文。
2. 给用户过目，允许增删/改。
3. 用 subagent 模拟触发判断（把 query + 当前 description 交给 subagent，问它“这个 query 会不会触发该技能？”），统计触发率。
4. 根据失败案例改写 description，重复直到在难例上也稳定。
5. 展示 before/after 给用户确认。

### 6. 落盘

- **先让用户点名目标根，再写文件。** 可以给推荐（通用技能：用户级通用技能目录，如 `~/.agents/skills/<name>/SKILL.md`；项目技能：该项目的技能目录），但推荐不等于决定——路径由用户点头。用户没给就问一下，别替他选。
- **不要因为「当前跑的是哪个 agent」就往那个 agent 的私有目录放**（`.claude/skills/`、`.codex/skills/` 之类）。技能本体是 agent 无关的文本，agent 私有目录不是默认归宿；用户明确要装进某个 agent 的目录时照办。
- **目标目录不存在，不要凭空创建。** 先说「`<路径>` 不存在，要建吗」，得到同意再建。
- **目标位置已有同名技能，不要静默覆盖。** 先讲清旧的是什么、要改成什么，确认后再替换。
- 保存后确认能被发现，目录名与 `name` 一致（不一致时以 frontmatter 的 `name` 为准）。
- 告诉用户：技能已保存，放在哪个根、影响范围是什么。

## 修改现有技能

- **保留原名**：不要随便改成 `xxx-v2`；目录名和 frontmatter `name` 都保持原样。
- 如果原文件只读，先复制到可写位置编辑，再替换回去。
- 保存后通常立即生效；如果当前会话没看到新技能，重开会话即可。
- 改 description 前先想清楚触发意图变化，避免破坏已有调用场景。

## 风格与原则

- **不惊喜原则**：技能里不能有恶意代码、利用代码、隐藏意图的内容；不要帮用户做误导性或越权的技能。
- **解释 why**：LLM 理解原因后能超越死板步骤；如果发现自己写满 ALL CAPS 的 “ALWAYS/NEVER”，先想想能不能改成解释动机。
- **保持精简**：删掉不产生价值的段落；读测试记录看 agent 是否在无效工作上浪费时间。
- **防过拟合**：迭代时不要只修测试用例里的具体毛病，要概括成通用模式，否则技能换个输入就废了。
- **写草稿后重读一遍**，用“新眼睛”检查是否清晰、有无矛盾。

- 当前环境有打包/分享机制就用，没有就直接给目录。
